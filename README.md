        # temporal — Идемпотентность активностей

        Homework-шаблон для урока **l4_idempotency** (Идемпотентность активностей) на платформе Vibe Learn.

        ## Что делать

        Реализуй PaymentWorkflow на Go SDK (go.temporal.io/sdk) с активностью ChargeCard,
которая пишет в in-memory «биллинг» (map order_id → charges). Симулируй at-least-once:
тест заставляет активность «выполнить эффект, затем упасть до рапорта», провоцируя
ретрай. Версия 1 (наивная, без ключа) — тест должен показать двойное списание. Версия 2:
детерминированный idempotency key из activity.GetInfo (RunID+ActivityID), а «биллинг»
дедуплицирует по ключу. Тесты через TestWorkflowEnvironment проверят: наивная версия
списывает дважды, идемпотентная — ровно один раз, несмотря на ретрай.

## Контекст (из transfer-задачи урока)

Платёжный сервис на Temporal. Активность ChargeCard вызывает внутренний биллинг
HTTP-методом POST /charge с телом {order_id, amount}. На проде завели автоскейлинг
подов-воркеров и стали ловить жалобы: иногда клиента списывают дважды за один заказ.
Логи показывают: списания происходят при рестартах/убийствах подов. Разработчик
предлагает «фикс»: генерировать uuid.New() внутри ChargeCard и слать его как
Idempotency-Key в биллинг.

**Вопрос:** разбери ситуацию. Опиши:
(a) механизм, почему автоскейлинг подов вызывает двойное списание;
(b) почему uuid.New() внутри активности НЕ починит проблему;
(c) как сделать правильно (детерминированный ключ + что должен делать биллинг).

## Recap из урока

- **#1 production-gotcha:** оркестрация exactly-once, но **побочный эффект активности — at-least-once**. Активность может выполниться дважды → активности ОБЯЗАНЫ быть идемпотентными.
- Сценарий: воркер сделал эффект (списал деньги), но **упал ДО рапорта** Temporal → в истории нет завершения → RetryPolicy ретраит → эффект повторяется. Это штатно (деплои, OOM, автоскейлинг).
- Техника: **детерминированный idempotency key** из `activity.GetInfo` (RunID + ActivityID), одинаковый на всех ретраях, передаётся downstream. `uuid.New()`/`time.Now()` внутри активности — **антипаттерн** (новый ключ каждый ретрай).
- Без idempotency-ключей у downstream: **dedup-таблица** (уникальный индекс по ключу) или **conditional write** (ON CONFLICT DO NOTHING). Read-only и естественно идемпотентные (`SET x=value`) — безопасны.
- Не путай: **детерминизм workflow** (оркестрация) ≠ **идемпотентность activity** (эффекты). Разные свойства на разных уровнях. Компенсации саги тоже at-least-once → тоже идемпотентны.

        ## Как работать

        1. Платформа Vibe Learn создаёт копию этого репо в твоём GitHub-аккаунте по клику «Начать домашку» на странице урока (через GitHub `/generate`, codecrafters-pattern).
        2. Склонируй копию локально, реализуй TODO в `main.go` (workflow + активности), прогони тесты, запушь.
        3. CI (`.github/workflows/ci.yml`) запускает `go vet` + `go test ./...` на каждый push. Платформа слушает результат через webhook от GitHub Actions и обновляет статус домашки на странице урока.

        ## Локальное окружение

        - Go 1.22+
        - SDK: `go.temporal.io/sdk`
        - Docker + docker-compose — `docker compose up` поднимает Temporal dev server на `:7233` + Web UI на `:8233`. Адрес переопределяется через env `TEMPORAL_ADDRESS` (дефолт `localhost:7233`).
        - Юнит-тесты на `testsuite.TestWorkflowEnvironment` (активности замоканы) бегут в CI БЕЗ сервера; интеграционный тест включается через `TEMPORAL_INTEGRATION=1`.

        ## Запуск

        ```bash
        # Поднять локальный Temporal dev server + UI
        docker compose up -d
        # Web UI: http://localhost:8233

        # Прогнать тесты (юнит на TestWorkflowEnvironment — без сервера;
        # интеграционный включается через TEMPORAL_INTEGRATION=1)
        go test ./...
        TEMPORAL_INTEGRATION=1 go test ./...

        # Запустить воркер (регистрирует workflow + активности, слушает task queue)
        go run .
        ```
